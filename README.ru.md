# Поиск услуг Avito — кандидатогенерация (Recall@50)

> Полная версия на английском — [README.md](README.md). Этот файл —
> её перевод для удобства проверки.

Этап кандидатогенерации для каскадного поиска, описанного в задаче: по
короткому поисковому запросу вернуть до 50 `item_id`-кандидатов из
`benchmark_items.parquet` для последующего ранжирования. Оптимизируется
метрика **Recall@50**.

## Коротко

- **Метод**: BM25 (классический разреженный лексический поиск, написан
  с нуля на scipy/numpy — без `rank_bm25` и других готовых библиотек
  поиска) поверх взвешенного bag-of-words из заголовка / описания /
  структурированных параметров, **плюс буст по совпадению локации,
  который оказался главным сигналом во всей задаче** (услуги на Avito —
  это гиперлокальный рынок, подробнее ниже), плюс небольшой prior по
  микрокатегории.
- **Без внешних API и скачиваемых моделей.** Всё считается локально на
  pandas/numpy/scipy/scikit-learn.
- **Офлайн-валидация** (holdout-сплит внутри `train.parquet`, см. ниже):
  **Recall@50 ≈ 0,827** (против 0,19 у одного только текстового BM25);
  последний прирост дало небольшое нечёткое сопоставление по символьным
  n-граммам поверх всего остального (см. §0е).
- **История реальных результатов на бенчмарке**, отслеженная по пяти
  отправленным итерациям пайплайна по мере уточнения сигнала по
  локации (расследование каждого шага — в разделе «Найденные ошибки»):

  | Итерация | Recall@50 офлайн | Recall@50 на реальном бенчмарке |
  |---|---|---|
  | 1. Только прямой буст по локации | 0.751 | 0.7182 |
  | 2. + редирект локации (без взвешивания, top-1 хаб) | 0.800 | 0.7408 |
  | 3. + редирект, взвешенный по уверенности | 0.804 | 0.7510 |
  | 4. + top-5 хабов редиректа вместо top-1 | 0.812 | 0.7539 |
  | 5. + гарантированное расширение кандидатов по локации | 0.823 | *не отправлялась отдельно — решили продолжить эксперименты, см. ниже* |
  | 6. + нечёткое сопоставление по символьным n-граммам (текущая) | 0.827 | *ожидается* |

  Взвешивание по уверенности (итерация 3) дало на реальных данных
  **больший** прирост, чем предсказывала офлайн-оценка (+0,0102 реальный
  против +0,0037 офлайн). А вот итерация 4 (top-5 хабов), наоборот, дала
  на реальных данных заметно **меньший** прирост, чем предсказывал
  офлайн (+0,0029 реальный против +0,008 офлайн) — убывающая отдача от
  дальнейшей настройки ОДНОГО И ТОГО ЖЕ механизма сопоставления по
  локации. Именно это и натолкнуло на итерацию 5: структурно другое
  исправление (расширение того, КАКИЕ объявления вообще могут стать
  кандидатами, а не очередная подстройка того, как уже найденные
  кандидаты бустятся).
- Воспроизведение:
  ```bash
  pip install -r requirements.txt
  # положить train.parquet, benchmark_queries.parquet, benchmark_items.parquet в ./data/
  python3 scripts/generate_answer.py
  ```
  Скрипт пишет `answer.csv` в корень проекта — побайтово тот же файл,
  что был отправлен на проверку (пайплайн полностью детерминирован: нет
  случайных выборок, нет недетерминизма GPU).

## Используемые данные и признаки

| Используется для поиска | Поле(я) | Почему |
|---|---|---|
| Текст объявления | `item_title_raw`, `item_infm_params_text`, `item_description_raw` | Единственный контент, который может лексически совпасть со свободным текстом запроса. |
| Текст запроса | `search_query`, `search_infm_params_text` | Та же логика со стороны запроса. |
| **Локация** | `search_location_id` против `item_location_id` | **Главный сигнал** — см. ниже. |
| Категория объявления | `item_microcat_id` | Вторичный prior для переранжирования, полезен именно после того, как локация уже учтена (см. «Метод»). |
| `search_category` | — | Не используется: 91% и train-, и benchmark-запросов имеют одно и то же значение (`114`), т.е. признак почти не несёт информации в этом датасете. |
| Цена, рейтинг, флаги скрытого телефона/сообщений | — | Не используются в этом решении (см. «Что бы я попробовала дальше»). |

Всё остальное (`item_price`, `item_rating`, `item_is_phone_hidden` и
т.д.) полезно для последующего этапа *ранжирования*, но не очевидно
полезно для *кандидатогенерации* — её единственная задача — не потерять
релевантное объявление, ей ещё не важно, у исполнителя 5 звёзд или 3.

## Метод

### 0. Совпадение локации — главная находка этого решения

Прежде чем настраивать детали текстового скоринга, я проверила прямо по
`train.parquet` простую гипотезу: для объявления, которое пользователь
реально выбрал, как часто `item_location_id` в точности равен
`search_location_id` того запроса, по которому это объявление нашли?

**83,1% случаев.**

Задним числом это совершенно логично: услуги на Avito (мастер маникюра,
электрик, репетитор) — это по своей природе **локальный** рынок. В
корпусе тысячи почти одинаковых по формулировке объявлений на массовые
запросы («маникюр», «ремонт стиральных машин») по всей стране, и
обычный лексический BM25 никак не может предпочесть объявление, которое
реально находится в городе пользователя, — он ранжирует идеально
совпадающее по тексту объявление из другого города точно так же, как
соседнее. На корпусе в 189 тыс. объявлений по всей стране это означает,
что настоящий (локальный) ответ регулярно вытесняется из топ-50
текстово похожими, но географически нерелевантными объявлениями.

Добавление буста по совпадению локации в скор ранжирования
(`src/ranking.py::boosted_top_k`, параметр `alpha_location`) подняло
офлайн Recall@50 с **0,19 до 0,75** — на порядок больше эффекта, чем у
любого другого изменения в этом решении, вместе взятого. В первой версии
решения я этот сигнал не использовала и нашла его, только когда вернулась
к вопросу, почему один текстовый BM25 работает настолько хуже, чем
выглядели «простыми» некоторые примеры запросов из условия — хороший
повод не забывать перепроверять даже признаки, которые на первый взгляд
«относятся» к этапу ранжирования, а не отбора кандидатов.

Реализация: мягкий аддитивный буст, а не жёсткий фильтр — объявления не
из локации поиска никогда не исключаются, а только ранжируются ниже,
поэтому запрос без вообще каких-либо локальных объявлений всё равно
корректно откатывается на лучший текстовый результат по всей стране.
Буст масштабируется относительно максимального BM25-скора ЭТОГО
конкретного запроса (`alpha_location * max_score`), поэтому одно и то
же значение `alpha_location` работает одинаково хорошо для запросов с
очень разным масштабом скоров. Recall@50 выходит на плато уже при
`alpha_location=1.0` (проверено вплоть до 50 — без дальнейших изменений,
см. `scripts/run_validation.py`): при этом значении буст уже
гарантированно выводит любое объявление из подходящей локации выше
любого объявления из другой локации для этого запроса, дальше
увеличивать нечего. Беру наименьшее значение, при котором достигается
это плато.

### 0б. Редирект локации — вторая по значимости находка

Я сначала отправила решение только с прямым бустом по локации выше, и
оно получило **0,7182** на реальном бенчмарке (против 0,751 офлайн — см.
пункт 1 «Найденных ошибок» про то, к чему привело расследование этого
разрыва). Разбираясь, ПОЧЕМУ реальный результат оказался ниже
офлайн-оценки, я обнаружила: **у 17,4% запросов бенчмарка (427 из 2452)
`search_location_id`, для которого в `benchmark_items.parquet` нет
вообще НИ ОДНОГО объявления** с таким же `item_location_id`. Для таких
запросов буст по локации выше просто никогда не срабатывает — сравнивать
не с чем — и ранжирование тихо откатывается на чистый текст+категорию,
то есть ровно на уровень baseline ~0,19.

Это не случайные id: это реальные, часто встречающиеся небольшие
города/районы, у которых, судя по всему, просто нет своих исполнителей
на Avito. Проверка по `train.parquet` показала: все 58 различных
`search_location_id`, стоящих за этими 427 запросами, встречаются там
тысячи раз как локации ПОИСКА, и у каждого есть один явно доминирующий
item_location_id, к которому такие поиски фактически приводят (70-100%
случаев в проверенных мной примерах) — почти наверняка это ближайший
крупный город или хаб, который реально обслуживает эту территорию. Это
не специфика именно проблемных локаций: среди ВСЕХ различных значений
`search_location_id` в `train.parquet` у 44% самый частый итоговый
`item_location_id` отличается от самой локации поиска — просто для
благополучных, хорошо обслуженных городов этот доминирующий адресат
обычно совпадает с самим городом, поэтому незаметен, пока специально не
проверишь.

`src/ranking.py::build_location_redirect` выучивает это отображение
(`search_location_id -> исторически частые item_location_id`) прямо по
`train.parquet`, а буст по локации после этого проверяет совпадение с
исходной локацией поиска ИЛИ с её редирект-адресатами (это мягкое
объединение, а не замена — для 82,6% запросов с нормальными, хорошо
обслуженными локациями это почти ничего не меняет, поскольку топ-адресат
редиректа обычно и есть сама локация поиска). Повторная отправка только
с top-1 адресатом редиректа подняла реальный результат бенчмарка с
0,7182 до 0,7408.

### 0в. Взвешивание редиректа по его собственной уверенности

После редиректа выше я проверила: теперь 100% запросов бенчмарка имеют
ХОТЬ КАКОЙ-ТО кандидат с бустом по локации (прямой или по редиректу). Но
«мода» (самый частый адресат) не везде одинаково надёжна: доля
исторических поисков, реально приводивших к этой моде, варьируется от
~5% до 100% в зависимости от search_location_id — где-то это уверенный,
почти гарантированный вывод, а где-то почти угадывание между двумя
примерно равновероятными соседними хабами. Пайплайн применял ко всем
этим случаям одинаковый буст, доверяя 50%-й догадке ровно так же, как
83%-му прямому совпадению.

`build_location_redirect` дополнительно возвращает эту уверенность (долю
исторических поисков из данной локации, реально приведших к каждому
возвращённому адресату), и буст по совпадению только с редиректом (не с
прямой локацией поиска) масштабируется ею:
`confidence * alpha_location * max_score`, тогда как настоящее прямое
совпадение по-прежнему всегда получает полный, невзвешенный буст (это
факт про само объявление, а не историческая догадка). Я также проверила
вариант с жёстким порогом уверенности (буст применяется только выше
порога) — он оказался ХУЖЕ плавного взвешивания при любом проверенном
пороге (0,783 при пороге 0,8 против 0,786 у взвешивания, оба измерены
только с одним, самым частым адресатом редиректа): порог полностью
убирает буст для локаций с низкой уверенностью, а даже посредственная
гео-догадка явно лучше, чем вообще никакого гео-сигнала. Повторная
отправка со взвешиванием по уверенности снова улучшила реальный
результат, с 0,7408 до 0,7510 — причём реальный прирост (+0,0102)
оказался БОЛЬШЕ, чем предсказывала офлайн-оценка (+0,0037): обнадёживающий
знак, что это направление действительно хорошо обобщается, а не
подгоняется под офлайн-валидацию.

### 0г. Больше одного адресата редиректа

Редирект выше использовал только один, самый частый исторический
адресат для каждой локации поиска. Но у многих search_location_id
исторические поиски делятся сразу между НЕСКОЛЬКИМИ соседними хабами —
например 45% в один соседний город и 40% в другой — и top-1 редирект
захватывает только большую долю. `build_location_redirect` теперь
возвращает до `top_n` адресатов на локацию поиска (каждый со своей
confidence, суммируются так же, как раньше), а не только моду. Recall@50
стабильно рос с ростом top_n: **0,786 (n=1) → 0,792 (n=2) → 0,794 (n=4)
→ 0,794 (n=5)**, выходя на плато примерно на n=5 (n=6 оказался чуть
хуже — 0,7942 против 0,7942 округляются одинаково, но шестой по частоте
адресат для большинства локаций уже чистый шум). `top_n=5` используется
в финальном пайплайне. Повторная отправка с этим изменением дала на
реальных данных заметно меньший прирост, чем предсказывал офлайн
(0,7510 → 0,7539 реальный против 0,804 → 0,812 офлайн) — явный признак
убывающей отдачи от дальнейшей настройки того, НАСКОЛЬКО сильно
доверять совпадениям по локации, что и привело к следующему,
структурно другому исправлению ниже.

### 0д. Гарантия кандидатов по локации, а не только их переранжирование

Все сигналы по локации до этого момента (§0–§0г) только ПЕРЕРАНЖИРОВЫВАЛИ
объявления, которые BM25 и так уже нашёл по какому-то лексическому
пересечению с запросом — они могли поднять объявление из нужной локации
на вершину списка, но никогда не могли ДОБАВИТЬ объявление, у которого с
текстом запроса вообще нет общих слов. Я напрямую проверила, насколько
часто это реально мешает: **у 3,1% всех релевантных объявлений** (в
офлайн-валидации) локация в точности правильная (прямая или один из
top-5 редирект-адресатов), но с текстом запроса нет НИ ОДНОГО общего
слова — BM25 их вообще не рассматривает, сколько бы буста по локации ни
было на кону.

`src/ranking.py::build_location_index` строит один раз индекс
"location_id -> позиции объявлений", и `boosted_top_k` использует его,
чтобы БЕЗУСЛОВНО добавлять в кандидаты все объявления из подходящих для
запроса локаций — с BM25-скором ровно 0, если текст не совпал вообще, и
тогда единственным источником их скора становятся бусты по локации (и
микрокатегории). Я проверила ограничение сверху на размер локации
(чтобы не перебирать тысячи объявлений мегагорода вроде Москвы на каждый
запрос) и обнаружила, что Recall@50 продолжает расти вплоть до полного
отсутствия ограничения:

| Максимум добавляемых объявлений на локацию | Recall@50 |
|---|---|
| 20 | 0,8121 |
| 100 | 0,8138 |
| 500 | 0,8162 |
| 2 000 | 0,8202 |
| 10 000 | 0,8228 |
| **без ограничения (финал)** | **0,8234** |

Это логично, если задуматься: лишние кандидаты могут конкурировать
только за нижние строчки топ-50 (настоящие текстовые совпадения, у
которых и так есть полный буст по локации, никогда не вытесняются), так
что добавление большего числа кандидатов в принципе не может НАВРЕДИТЬ —
только стоит вычислительного времени для очень крупных локаций, что на
практике оказалось приемлемым (полный прогон по бенчмарку всё ещё
укладывается примерно в две минуты). Это самый крупный офлайн-скачок со
времён самого первого буста по локации (§0) — ожидаемо, ведь это
исправление структурного пробела, а не подстройка порога внутри уже
работающего механизма.

### 0е. Нечёткое сопоставление по символьным n-граммам как второй ретривер

Всё до §0д по-прежнему опирается на точный по словам BM25: запрос и
объявление связаны, только если у них есть хотя бы один одинаковый
токен. Это упускает словоформы, опечатки и по-разному разбитые составные
слова — например, запрос «маникюрный мастер» и объявление «мастер
маникюра» делят на уровне точных токенов только слово «мастер», но на
уровне символьных 3-5-грамм у них общая большая часть подстрок («маникюр…»
и т.д.). Этот слепой участок особенно усиливается вместе с §0д: у
объявлений, попавших в кандидаты только через расширение по локации, с
BM25-скором ровно 0, вообще нет никакого другого текстового сигнала —
и в этом случае именно символьное сходство остаётся единственным
способом отличить действительно похожее объявление от случайного,
которое просто оказалось в том же городе.

`src/fuzzy.py::FuzzyIndex` строит TF-IDF-индекс по символьным 3-5-граммам
(`analyzer="char_wb"`) вместо слов, зеркаля API `BM25Index`
(`.fit()` / `.score_chunked()`), чтобы включаться в тот же цикл
ранжирования как второй, независимый скор похожести. `max_df=0.5` здесь
важен даже больше, чем для BM25: различных символьных n-грамм на порядок
меньше, чем слов, поэтому без отсечки самые частые из них (обрывки
типичных окончаний) встречаются почти в каждом документе и грозят той же
проблемой с плотностью/памятью, что описана в §2 / пункте 4 «Найденных
ошибок».

Перебор веса (`alpha_fuzzy`) на офлайн-валидации, поверх полного пайплайна
из §0д (базовый Recall@50 = 0,8234):

| alpha_fuzzy | Recall@50 |
|---|---|
| 0.05 | 0.8261 |
| 0.08 | 0.8261 |
| **0.1 (выбрано)** | **0.8268** |
| 0.12 | 0.8253 |
| 0.15 | 0.8262 |
| 0.2 | 0.8256 |
| 0.3 | 0.8257 |
| 0.5 | 0.8229 |
| 1.0 | 0.8068 |
| 2.0 | 0.7432 |

Сигнал реально полезен, но только в узком диапазоне небольших весов: он
гораздо более шумный, чем точное совпадение слов (короткие, никак не
связанные по смыслу слова нередко случайно делят много символьных
n-грамм), поэтому при большом весе он начинает перевешивать надёжные
сигналы (BM25, локацию, категорию) вместо того, чтобы просто дозаполнять
их слепые зоны. В финальном пайплайне используется `alpha_fuzzy=0.1`.

**Также проверено и не дало эффекта**: перебор по сетке собственных
гиперпараметров BM25 `k1`/`b` (в литературе стандартные значения —
`k1=1.5, b=0.75`) не нашёл ни одной конфигурации лучше значений по
умолчанию на этом датасете: каждое проверенное значение дало результат
не выше базового (`b=0.0` в точности повторил базовые 0.8234, все
остальные комбинации оказались строго хуже). Задокументировано здесь как
отрицательный результат, а не оставлено непроверенным.

### 1. Предобработка текста (`src/text_utils.py`)

Приведение к нижнему регистру, нормализация `ё`→`е`, вручную составленный
список из ~130 русских стоп-слов (без скачиваний — чтобы решение
оставалось полностью офлайн-воспроизводимым; корпус стоп-слов из nltk
потребовал бы `nltk.download()` во время выполнения, что запрещено
условием «без обращений к внешним API»). Без стемминга/лемматизации:
объявления услуг на Avito полны брендов, профессионального жаргона и
редких составных слов, и быстрая ручная проверка показала, что
поверхностные токены уже дают сильное лексическое пересечение для этого
домена — обобщённый стеммер с большей вероятностью склеил бы разные
слова, чем помог.

### 2. BM25 со взвешенными полями (`src/bm25.py`, `src/data_prep.py`)

Библиотека `rank_bm25` не используется — она считает скор запрос-документ
чистым Python-циклом по каждому документу, что слишком медленно для
~190 тыс. объявлений × ~2.5 тыс. запросов. Вместо этого BM25 (формула
Robertson & Sparck Jones) реализован как разреженная матричная алгебра
поверх `CountVectorizer` из scikit-learn — после fit полный прогон
занимает меньше минуты.

Заголовок, структурированные параметры и описание объединяются в один
bag-of-words на объявление (и на запрос — из `search_query` +
`search_infm_params_text`) через **повторение токенов поля N раз** перед
подсчётом — дешёвая замена честному BM25 по отдельным полям. Перебор по
сетке на офлайн-валидации (`scripts/run_validation.py`) для триплетов
весов (заголовок/параметры/описание) показал, что **5 / 3 / 1** —
минимальные веса, при которых recall выходит на плато (числа ниже — для
текстового BM25 самого по себе, ДО какого-либо буста по локации):

| веса (заголовок/параметры/описание) | Recall@50 |
|---|---|
| 1 / 1 / 1 (без весов) | 0.174 |
| 3 / 2 / 0 (без описания) | 0.154 |
| 3 / 2 / 1 | 0.182 |
| **5 / 3 / 1 (выбрано)** | **0.185** |
| 7 / 4 / 1 | 0.184 (прироста нет) |
| 5 / 3 / 2 | 0.185 (прироста нет) |

Полное исключение описания стоило ~0.03 Recall@50 — оно всё же несёт
реальный сигнал, несмотря на то что это самое «шумное» поле.

**Найденная проблема со словарём** (подробнее в «Найденные ошибки»
ниже): `item_infm_params_text` — это поле с фиксированным шаблоном
(«Вид услуги ...», «Место оказания услуг ...», «Тип стоимости за
услугу ...», сокращения дней недели и т.д.). До фильтрации слова-метки
шаблона — *место*, *оказания*, *услуг*, *вид*, *тип*, *стоимости* —
встречались в 95–100% из всех 344 825 объявлений. Так как скор
запрос↔объявление — это разреженное скалярное произведение, общие для
всех документов термины делают матрицу скоров (запрос × объявление)
**структурно плотной** — на выборке из 30 тыс. объявлений «сырая»
матрица схожести объявление-объявление оказалась **плотной на 100%**, а
на полном корпусе память процесса (RSS) превысила **10 ГБ**, что
подвесило машину. **Исправление**: `CountVectorizer(max_df=0.4)` —
отбросить любой термин, встречающийся более чем в 40% объявлений; это
убирает только почти-универсальные шаблонные слова (реальные содержательные
слова вроде «ремонт» с df≈0.32 остаются) и снижает потребление памяти на
порядок без потери recall. Дополнительно расчёт скоров для запросов
выполняется чанками (`BM25Index.score_chunked`, по 200 запросов за раз),
чтобы пиковая память никогда не масштабировалась как полное произведение
запрос × объявление.

### 3. Исторические priors из `train.parquet` (`src/ranking.py`)

Помимо локации, ещё два сигнала были опробованы, выучены по парам
запрос→объявление из `train.parquet` и наложены поверх BM25 + буста по
локации, ни разу не касаясь разметки бенчмарка (её просто не существует):

- **Prior по микрокатегории**: буст объявлениям, чей `item_microcat_id`
  совпадает с микрокатегорией, исторически выбираемой для этого же
  текста запроса. **До появления буста по локации этот сигнал стабильно
  *ухудшал*** офлайн-recall (0.182 → 0.176 по мере роста веса).
  **После добавления буста по локации тот же сигнал *помогает*** (ещё
  примерно +0.02 Recall@50 при лучшем весе — см. пункт 6 раздела
  «Найденные ошибки», почему один и тот же prior переходит из вредного
  в полезный в зависимости от того, что ещё уже учтено в ранжировании;
  это самый интересный методологический урок в этом проекте).
- **Меморизация исторического объявления**, проверены два варианта:
  - Привязанная только к тексту запроса: была полезна поверх одного
    текстового BM25, но стала избыточной (небольшой, стабильно
    отрицательный эффект в пределах шума) после добавления локации —
    один и тот же текст запроса ведёт к РАЗНЫМ объявлениям в разных
    городах, поэтому единый «самый частый по стране» исторический ответ
    перестаёт быть полезным, когда локация уже учтена явно.
  - Привязанная к паре (текст запроса, `search_location_id`) вместе —
    гораздо более точный ключ (81% таких пар в `train.parquet` дают
    ровно один уникальный исторический ответ против 60% для одного
    текста), и она действительно немного помогала офлайн. Но проверка
    её реального покрытия именно на корпусе бенчмарка (тем же методом,
    что и в пункте 1 «Найденных ошибок») показала, что она сработает
    лишь для **3,6%** запросов бенчмарка — большая часть её
    офлайн-пользы происходит от более крупного и плотного
    офлайн-корпуса на основе train, а не от чего-то, что пропорционально
    переносится на меньший реальный корпус. Учитывая добавляемую
    сложность ради настолько узкого сигнала, я не стала включать её в
    отправленный пайплайн (задокументированное решение, а не доказанный
    вред).

  Обе версии (`build_memo_prior`) оставлены рабочими и по-прежнему
  задействованы в `scripts/run_validation.py`, чтобы эти сравнения
  оставались воспроизводимыми; ни одна не используется в
  `scripts/generate_answer.py`.

### 4. Финальное ранжирование

Для каждого запроса: скор BM25 по всему корпусу объявлений → гарантировать,
что все объявления из подходящих запросу локаций стали кандидатами (§0д,
даже с нулевым текстовым скором) → добавить буст по совпадению локации
(полная сила для прямого совпадения, взвешенная по уверенности сила для
каждого из до 5 совпадений по редиректу) → добавить буст по совпадению
микрокатегории → добавить скор нечёткого сопоставления по символьным
n-граммам (§0е) → выбрать топ-50 по итоговому скору.

## Как проверялось качество перед отправкой

В `train.parquet` нет id запроса — каждая строка это пара
`(запрос, выбранное объявление)`. Я восстановила **354 463 уникальных
экземпляра запроса**, сгруппировав строки по полному набору признаков
запроса (`search_query`, `search_location_id`,
`search_is_delivery_search`, `search_infm_params_text`,
`search_category`); item_id внутри группы образуют её множество
релевантных объявлений (в среднем 1.32 релевантных объявления на запрос
— совпадает с описанием в задании «обычно одно-два»).

Экземпляры запросов разбиты на **FIT/EVAL** (5000 EVAL-экземпляров, с
фиксированным seed — увеличено с исходных 2000, когда стало ясно, что
некоторые сравнения гиперпараметров были в пределах шума меньшей
выборки). FIT играет роль исторического лога запросов (на нём строится
BM25 и priors), EVAL — роль отложенных запросов бенчмарка. Корпус
объявлений для поиска — все уникальные объявления *всего* train.parquet
(344 825 объявлений) — знание корпуса не является утечкой разметки,
утечкой было бы только знание ответа для конкретного EVAL-запроса, а
оно нигде не используется.

Такое разбиение специально сделано реалистичным, а не искусственно
лёгким: я напрямую проверила на `benchmark_queries.parquet`, что
**37.0%** текстов реальных запросов бенчмарка дословно встречаются
где-то в `train.parquet` — это почти совпадает с тем, что даёт случайное
разбиение самого train.parquet, — то есть офлайн-оценка должна разумно
переноситься на реальный результат бенчмарка (хотя и не идеально — см.
пункт 1 «Найденных ошибок» про конкретный случай, когда перенос не
сработал, и как этот разрыв сам по себе стал источником реального
улучшения).

Полная динамика на офлайн-EVAL (все числа воспроизводимы через
`scripts/run_validation.py`):

| Конфигурация | Recall@50 |
|---|---|
| Только текстовый BM25 (веса 5/3/1) | 0.1896 |
| + буст по локации, только прямое совпадение (`alpha_location=1.0`) | 0.7507 |
| + редирект локации, top-1 адресат, без взвешивания | 0.7816 |
| + редирект локации, top-1 адресат, взвешенный по уверенности | 0.7862 |
| + редирект локации, top-5 адресатов, взвешенный по уверенности | 0.7942 |
| + prior по микрокатегории (`alpha_microcat=0.2`) | 0.8119 |
| + меморизация (по тексту запроса) поверх всего этого | 0.8113 (прироста нет, убрана) |
| + гарантированное расширение кандидатов по локации (§0д) | 0.8234 |
| + нечёткое сопоставление по символьным n-граммам, `alpha_fuzzy=0.1` (§0е) | **0.8268** (финал) |

Реальные результаты бенчмарка по фактически отправленным итерациям
пайплайна (см. также таблицу в «Коротко»): **0,7182** (только прямое
совпадение локации) → **0,7408** (+ top-1 редирект без взвешивания) →
**0,7510** (+ взвешивание по уверенности) → **0,7539** (+ top-5
адресатов редиректа) → *ожидается* (+ гарантированное расширение
кандидатов по локации, эта версия).

## Найденные ошибки и что было сделано

1. **Реальный результат на бенчмарке ниже офлайн-оценки привёл к находке
   второго важного сигнала.** Первая отправленная версия этого пайплайна
   (текстовый BM25 + прямой буст по локации + prior по микрокатегории,
   без редиректа) получила на реальном бенчмарке 0.7182 против
   офлайн-оценки 0.751 — правдоподобный, но реальный разрыв в
   обобщающей способности. Вместо того чтобы просто принять его, я
   напрямую проверила, не ведёт ли себя меньший (189 тыс. объявлений)
   корпус бенчмарка иначе, чем больший (345 тыс. объявлений) офлайн-корпус
   на основе train, в плане покрытия по локациям — и оказалось, что да:
   **у 17.4% запросов бенчмарка нет ни одного объявления в
   `benchmark_items.parquet` с точно таким же `search_location_id`**
   (против неявно более высокого покрытия в большем офлайн-корпусе).
   **Исправление**: редирект локации, описанный в «Методе» §0б. Повторная
   отправка подтвердила, что исправление действительно переносится на
   реальные данные: результат вырос до 0,7408. Следующий раунд
   (взвешивание по уверенности, §0в) перенёсся на реальные данные даже
   лучше, чем предсказывала офлайн-оценка, а вот раунд после него
   (top-5 адресатов редиректа, §0г) перенёсся ХУЖЕ предсказанного
   (+0,0029 реальный против +0,008 офлайн) — знак того, что просто
   докручивать один и тот же механизм сопоставления по локации уже
   не так эффективно. Именно это напрямую натолкнуло на §0д
   (гарантированное расширение кандидатов) — структурно другое
   исправление, а не ещё один поворот той же самой гайки.

2. **Один только текстовый BM25 изначально незаметно упускал самый
   главный сигнал.** Recall@50 около 0.19 выглядел низким для того,
   насколько специфичны большинство запросов («баня на дровах», «монтаж
   видеодомофонов»), что натолкнуло на прямую проверку, не объясняется
   ли этот разрыв локацией. Так и оказалось: у 83.1% исторически
   выбранных объявлений `item_location_id` совпадает с
   `search_location_id` запроса. **Исправление**: добавлен буст по
   совпадению локации, описанный в «Методе», §0 — вместе с уточнениями
   через редирект, взвешивание по уверенности, top-N адресатов и
   расширение кандидатов он отвечает практически за весь прирост
   качества в этом решении относительно простого текстового поиска.

3. **Даже с бустом по локации BM25 физически не мог показать объявления
   без лексического пересечения с запросом.** Все бусты вплоть до §0г
   только переранжировывают объявления, которые BM25 и так уже нашёл по
   общим словам, — объявление без единого общего слова с запросом
   никогда не могло попасть в кандидаты, сколько бы буста ни полагалось.
   Прямое измерение на офлайн-выборке: **3,1% всех релевантных
   объявлений** лежат в точно правильной локации, но имеют нулевое
   пересечение по словам с запросом. **Исправление**: `build_location_index`
   (§0д) безусловно добавляет в кандидаты все объявления из подходящих
   запросу локаций, с нулевым текстовым скором как базовым значением, если
   BM25 их не нашёл — это самый крупный офлайн-скачок со времён самого
   первого буста по локации, и он напрямую закрывает структурный пробел,
   а не подстраивает уже существующий механизм.

4. **Утечка памяти из-за шаблонного текста** (`item_infm_params_text` —
   поле с фиксированной формой, метки вроде «Вид услуги», «Место
   оказания услуг», названия дней недели — присутствуют в 95–100%
   объявлений). Без фильтрации это делает матрицу скоров запрос×объявление
   структурно плотной (подтверждена 100%-я плотность на выборке 30 тыс.
   объявлений), а на полном корпусе память процесса превысила 10 ГБ.
   **Исправление**: `max_df=0.4` в векторайзере плюс чанковый расчёт
   скоров (`BM25Index.score_chunked`), чтобы память была ограничена
   размером чанка независимо от плотности матрицы.

5. **Меморизационный prior сделал recall *хуже*, а не лучше**, когда был
   впервые добавлен без ограничений (0.182 → 0.150). Причина: точный текст
   запроса — гораздо более грубый ключ, чем реальный экземпляр запроса —
   общие однословные запросы вроде *«маникюр»* (5474 разных исторических
   объявления), *«массаж»* (3830), *«электрик»* (2451) в каждом городе
   ведут к разному исполнителю. Принудительное добавление всех
   исторических объявлений общего запроса в топ-50 заглушает
   специфичный для локации/текста BM25-ранжинг и вытесняет действительно
   релевантные кандидаты. **Исправление**: доверять этому prior только
   для текстов запросов с ≤5 разными историческими объявлениями (это
   покрывает 81% текстов запросов из train) и ограничивать добавляемые
   объявления топ-3 по частоте. (Позже, после добавления буста по
   локации, этот prior был убран из финального пайплайна целиком — см.
   §3 «Метода» — но сам приём ограничения остаётся правильным уроком про
   такого рода priors. Та же идея, обусловленная на пару текст+локация
   вместо одного текста, тоже была проверена — см. §3.)

6. **Prior по микрокатегории перешёл из вредного в полезный после
   добавления буста по локации — самый важный методологический урок
   этого проекта.** Без буста по локации этот prior стабильно ухудшал
   recall (0.182 → 0.176 по мере роста веса); с уже включённым бустом
   по локации ТОТ ЖЕ САМЫЙ prior помогает. Моя интерпретация: без
   локации кандидат-пул типичного запроса забит текстово похожими
   объявлениями со всей страны, и категорийный prior просто добавляет
   шум к уже шумному пулу. Когда локация (с учётом редиректа) сначала
   сужает пул до одного города или его хабов, оставшаяся неоднозначность
   (например, две разные микрокатегории с похожими словами) — это именно
   то, с чем категорийный prior справляется хорошо. **Вывод, который я
   держу в голове дальше**: сигнал, который выглядит вредным в изоляции,
   не обязательно плохой сам по себе — его можно оценивать только
   относительно того, что уже есть в ранжировании, поэтому после
   каждого изменения я перезапускала полный перебор, а не полагалась на
   более раннюю изолированную оценку.

7. **`search_category`** равен 114 у 91% и train-, и benchmark-запросов —
   это было проверено и признак сознательно не используется, чтобы не
   создавать ложного впечатления, будто фильтрация по категории делает
   полезную работу.

## Что бы я попробовала дальше при наличии времени

- **Более мягкий, основанный на расстоянии откат** для остаточных
  случаев, которые редирект локации не полностью решает (например, с
  использованием `item_latitude`/`item_longitude`). Я исследовала это
  напрямую: для примерно 36% объявлений `item_location_id` на деле
  представляет собой широкий регион, а не точный город (стандартное
  отклонение координат внутри одного `location_id` может достигать сотен
  км), поэтому наивное усреднение координат по `location_id` для
  получения «центральной точки» было бы вводящим в заблуждение именно
  для них — полноценная реализация сначала потребовала бы отличать
  локации уровня города от локаций уровня региона, что показалось мне
  задачей большего масштаба, чем позволяло время здесь.
- **BM25 по отдельным полям** (свой IDF для каждого поля) вместо трюка с
  повторением токенов — трюк является разумным приближением, но честный
  многопольный BM25F позволил бы заголовку/описанию иметь собственную
  статистику частоты документов.

## Заметки о воспроизводимости

- Детерминированность: в финальном пути `generate_answer.py` нет
  случайности (разбиение FIT/EVAL, используемое только в
  `run_validation.py`, зафиксировано seed'ом).

  сетевых обращений, нет предобученных эмбеддингов/моделей.

  требованиям задания: одна строка на каждый `query_id`, ≤50 уникальных
  `item_id` в строке, все id присутствуют в `benchmark_items.parquet`.
